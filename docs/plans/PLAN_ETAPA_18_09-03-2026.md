# Plan ETAPA 18 — Testing humano completo del sistema — 09-03-2026

**Fecha de ejecución:** 09-03-2026 (Semana 2 — Día 1)  
**Referencia:** docs/CHECKLIST_ETAPAS_PROYECTO.md (Etapas 18–22), docs/ENDPOINTS_API_Y_USO_FRONTEND.md  
**Objetivo:** Probar todos los flujos reales de la plataforma con pruebas humanas; detectar y corregir fallos antes de conectar nuevos endpoints.

---

## 1. Contexto y meta del día

- **Por qué este día:** La Semana 2 tiene como meta tener **todos los endpoints conectados al frontend**. Antes de añadir más conexiones, hay que asegurar que lo ya implementado funciona correctamente en uso real.
- **Entregable del día:** Plan de pruebas ejecutado, lista de fallos detectados (si los hay), correcciones aplicadas y validación QA. Sistema estable para pasar al Día 2 (dashboard con datos reales).

---

## 2. Actividades detalladas por paso

### Paso 1 — PO MASTER diseña plan de pruebas

| # | Actividad | Detalle | Tiempo est. |
|---|-----------|---------|-------------|
| 1.1 | Revisar flujos existentes | Listar todas las vistas y flujos según ENDPOINTS_API_Y_USO_FRONTEND.md: Login, Dashboard, Projects (listar, crear, detalle, archivar), Features (listar, crear, por proyecto), Stories (listar, crear), Sprints (listar, crear, detalle, cerrar), Releases (listar, crear, detalle), Incidents (listar, crear por proyecto), Documents (listar, crear, detalle), Reports (resumen proyecto/sprint, auditoría), Admin (usuarios, roles, foto, contraseña, métricas). | 20 min |
| 1.2 | Definir casos de prueba por flujo | Para cada flujo: caso “happy path” (éxito), caso con datos vacíos/empty state, caso de error (ej. red, 4xx). Usar como base docs/PLAN_PRUEBAS_PERSONALES_ETAPAS_13_A_17.md. | 30 min |
| 1.3 | Definir roles y datos de prueba | MASTER: todas las pantallas; EMPLOYEE: solo las permitidas; verificar que Admin y acciones restringidas no estén accesibles para EMPLOYEE. Decidir si se usan datos de BD existentes o dataset mínimo (proyecto, feature, story, sprint, release, incidente, documento). | 15 min |
| 1.4 | Documentar plan en un único documento | Crear o actualizar documento “Plan de pruebas ETAPA 18 — 09-03-2026” con: lista de flujos, casos por flujo, criterios de paso/fallo, responsable de ejecución. Guardar en docs/ (ej. docs/plans/PLAN_PRUEBAS_ETAPA_18_09-03-2026.md). | 15 min |

**Criterio de cierre paso 1:** Documento de plan de pruebas revisable por SYSTEM ARCHITECT y ejecutable por el equipo.

### Paso 2 — SYSTEM ARCHITECT valida cobertura

| # | Actividad | Detalle | Tiempo est. |
|---|-----------|---------|-------------|
| 2.1 | Revisar plan de pruebas | Comprobar que el plan cubre: autenticación (login, refresh, logout, me, roles), usuarios (CRUD, foto, contraseña), proyectos (CRUD, archive, features/sprints/incidents por proyecto), features (listar, crear, stories), stories (listar, crear), sprints (listar, crear, detalle, cerrar), releases (listar, crear, detalle), incidentes (listar, crear), documentos (listar, crear, detalle), reportes (summary proyecto/sprint, audit), system/metrics. | 20 min |
| 2.2 | Validar alineación con API | Verificar que los casos de prueba asumen las rutas y métodos reales de la API (ej. PATCH /sprints/:id/status si no existe /close). Anotar posibles desalineaciones para Etapa 21. | 15 min |
| 2.3 | Aprobar o devolver con comentarios | Firmar validación (en documento o checklist) o devolver al PO MASTER con ítems a completar. | 5 min |

**Criterio de cierre paso 2:** Plan de pruebas validado por SYSTEM ARCHITECT.

---

### Paso 3 — Equipo ejecuta pruebas humanas

| # | Actividad | Detalle | Tiempo est. |
|---|-----------|---------|-------------|
| 3.1 | Preparar entorno | Levantar backend y frontend (npm run dev o equivalente). Comprobar que la API responde (GET /api/v1/health). Tener al menos un usuario MASTER y opcionalmente uno EMPLOYEE. | 10 min |
| 3.2 | Ejecutar pruebas de autenticación | Login con credenciales válidas; comprobar redirección a dashboard; GET /auth/me reflejado en UI; logout; intento de acceso a ruta protegida sin login; refresh de token (dejar sesión abierta hasta que venza access token o simular 401). | 15 min |
| 3.3 | Ejecutar pruebas de gestión de usuarios | (Como MASTER) Ir a Admin → Usuarios: listar, crear usuario, editar (PUT), subir foto, cambiar contraseña, eliminar (soft delete). Comprobar listado de roles (GET /auth/roles) en formulario. Como EMPLOYEE: comprobar que no se accede a #/admin o que se muestra restricción. | 20 min |
| 3.4 | Ejecutar pruebas de proyectos | Listar proyectos en #/projects; filtrar por estado; crear proyecto; abrir detalle; desde detalle acceder a Features, Sprints, Incidents; archivar proyecto (MASTER). Empty state cuando no hay proyectos. | 15 min |
| 3.5 | Ejecutar pruebas de features | Seleccionar proyecto; listar features; crear feature; ver stories de una feature; crear story. Cambiar estado de feature si la UI lo expone (PATCH /features/:id/status). | 15 min |
| 3.6 | Ejecutar pruebas de stories | Listar stories (por feature/proyecto); crear story. Verificar que no haya errores en consola al cargar listados. | 10 min |
| 3.7 | Ejecutar pruebas de sprints | Listar sprints; crear sprint; abrir detalle de sprint; cerrar sprint (comprobar si la UI llama /close o /status). Empty state cuando no hay sprints. | 15 min |
| 3.8 | Ejecutar pruebas de releases | Listar releases; crear release; abrir detalle. Empty state. | 10 min |
| 3.9 | Ejecutar pruebas de documentos | Listar documentos; crear documento; abrir detalle. Empty state. | 10 min |
| 3.10 | Ejecutar pruebas de incidentes | Por proyecto: listar incidentes; crear incidente. Verificar que la lista y el formulario funcionan. | 10 min |
| 3.11 | Ejecutar pruebas de reportes | Ir a Reports; elegir proyecto y sprint; ver resumen de proyecto y resumen de sprint. Como MASTER: ver log de auditoría (GET /reports/audit). Comprobar que los datos mostrados coinciden con la API. | 15 min |
| 3.12 | Registrar resultados | Para cada caso: anotar OK o FALLO. En fallos: descripción, pasos para reproducir, mensaje de error (consola o UI), captura si aplica. Lista consolidada en documento o en docs/project-logs/resultados-pruebas-etapa-18-09-03-2026.md. | 20 min |

**Criterio de cierre paso 3:** Todas las pruebas ejecutadas y resultados documentados (lista de fallos clara para el MASTER DEVELOPER).

### Paso 4 — MASTER DEVELOPER corrige fallos

| # | Actividad | Detalle | Tiempo est. |
|---|-----------|---------|-------------|

| 4.2 | Corregir fallos bloqueantes y mayores | Por cada fallo: reproducir, localizar causa (frontend vs API), aplicar fix en frontend (esta etapa no toca backend). Probar de nuevo el caso. | Según cantidad (1–2 h) |
| 4.3 | Documentar cambios | Breve lista de archivos/cambios realizados (ej. “Ajuste en public/js/views/sprints.js para llamar PATCH /sprints/:id/status en lugar de /close”). | 15 min |
| 4.4 | Comunicar a QA | Indicar que las correcciones están listas para revalidación. | 5 min |

**Criterio de cierre paso 4:** Fallos críticos y mayores corregidos; menores anotados para Etapa 22 si no da tiempo.
