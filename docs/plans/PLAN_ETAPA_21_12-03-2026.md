# Plan ETAPA 21 — Alineación frontend / backend — 12-03-2026

**Fecha de ejecución:** 12-03-2026 (Semana 2 — Día 4)  
**Referencia:** docs/CHECKLIST_ETAPAS_PROYECTO.md (Etapas 18–22), docs/ENDPOINTS_API_Y_USO_FRONTEND.md, docs/CONTRATO_API.md, docs/openapi.yaml  
**Objetivo:** Corregir inconsistencias entre lo que el frontend envía y lo que la API espera (rutas, métodos, cuerpos); manejo correcto de errores HTTP y estados; workflows uniformes entre frontend y backend.

---

## 1. Contexto y meta del día

- **Por qué este día:** Tras conectar todos los endpoints (Día 3), pueden quedar desalineaciones: el frontend llama a una ruta que no existe (ej. PATCH /sprints/:id/close en lugar de PATCH /sprints/:id/status), envía cuerpos con nombres de campo distintos a los que espera la API, o no maneja bien 4xx/5xx. Este día se alinea contrato y comportamiento.
- **Entregable del día:** Llamadas del frontend 100% alineadas con la API; errores HTTP manejados en UI; mensajes de error consistentes con Response Layer v1; estados (workflows) uniformes.

---

## 2. Actividades detalladas por paso

### Paso 1 — PO MASTER documenta inconsistencias

| # | Actividad | Detalle | Tiempo est. |
|---|-----------|---------|-------------|
| 1.1 | Revisar ENDPOINTS_API_Y_USO_FRONTEND y notas | Recorrer el documento y la nota sobre Sprints (/close vs /status). Listar cualquier otra discrepancia ya conocida: rutas distintas, métodos (GET vs POST), nombres de body (camelCase vs snake_case, etc.). | 20 min |
| 1.2 | Revisar CONTRATO_API y openapi.yaml | Si existen, extraer rutas oficiales, métodos, esquemas de request/response y códigos de error. Comparar con lo que hace el frontend (buscar en public/js llamadas a api, fetch, axios). | 30 min |
| 1.3 | Ejecutar flujos y anotar errores | Durante pruebas rápidas: intentar cerrar sprint, cambiar estado de story, asignar story, etc. Anotar si alguna llamada devuelve 404, 400 o 422 y por qué (mensaje del backend). | 25 min |
| 1.4 | Redactar lista de inconsistencias | Documento “Inconsistencias frontend/backend ETAPA 21” con: (1) Ruta o flujo afectado, (2) Comportamiento actual del frontend, (3) Comportamiento esperado por la API, (4) Ajuste sugerido (cambio en frontend). Incluir también: manejo de errores (¿la UI muestra algo ante 4xx/5xx?) y mensajes/códigos de error. | 25 min |

**Criterio de cierre paso 1:** Lista clara de desalineaciones y de mejoras en manejo de errores para el MASTER DEVELOPER.

---

### Paso 2 — SYSTEM ARCHITECT define estándar

| # | Actividad | Detalle | Tiempo est. |
|---|-----------|---------|-------------|
| 2.1 | Definir estándar de rutas y métodos | A partir de openapi.yaml o CONTRATO_API, fijar la “fuente de verdad”: cada recurso tiene una ruta y método exactos. Documentar excepciones si las hay (ej. alias). Asegurar que PATCH /sprints/:id/status es el estándar y no /close a menos que el backend exponga /close. | 20 min |
| 2.2 | Definir estándar de manejo de errores | Cómo debe reaccionar el frontend: 401 → renovar token o redirigir a login; 403 → mensaje “Sin permisos”; 404 → “Recurso no encontrado”; 400/422 → mostrar mensaje del body (ej. errors[].message); 500 → mensaje genérico “Error del servidor”. Si existe Response Layer v1 con códigos de error, mapear códigos a mensajes de usuario. | 20 min |
| 2.3 | Definir convención de estados (workflows) | Por recurso (sprint, story, release, incident, change request, improvement, etc.): qué valores de status acepta la API y en qué orden. El frontend debe mostrar solo opciones válidas y enviar el valor exacto que espera el backend. Documentar en una tabla o en el mismo doc de inconsistencias. | 20 min |
| 2.4 | Entregar estándar al MASTER DEVELOPER | Documento “Estándar frontend–API ETAPA 21” (o sección en docs/) con: rutas correctas, manejo de errores, workflows. | 10 min |

**Criterio de cierre paso 2:** Estándar único y escrito para que el frontend se alinee.

---

### Paso 3 — MASTER DEVELOPER corrige frontend

| # | Actividad | Detalle | Tiempo est. |
|---|-----------|---------|-------------|
| 3.1 | Corregir rutas y métodos | Por cada inconsistencia documentada: cambiar la llamada en el código (public/js). Ejemplo: reemplazar PATCH /sprints/:id/close por PATCH /sprints/:id/status con body { status: "CLOSED" } o el valor que defina la API. Revisar todos los recursos: projects, features, stories, sprints, releases, incidents, change-requests, improvements, documents, users, organizations. | 1 h |
| 3.2 | Ajustar cuerpos de petición | Verificar que los objetos enviados en POST/PUT/PATCH coincidan con el esquema de la API (nombres de campos, tipos). Si la API espera snake_case y el front envía camelCase (o al revés), normalizar (en el cliente antes de enviar o en una capa api.js). | 45 min |
| 3.3 | Implementar manejo de errores HTTP | En la capa de llamadas a la API (api.js o equivalente): ante 4xx/5xx, no solo loguear; mostrar mensaje al usuario (toast, alert en formulario, o sección de error). 401: intentar refresh o redirigir a login. 403: mensaje “No tienes permisos”. 404: “No encontrado”. 400/422: extraer mensaje del body y mostrarlo. 500: “Error del servidor, inténtalo más tarde”. | 45 min |
| 3.4 | Unificar mensajes con Response Layer v1 | Si el backend devuelve códigos de error (ej. CODE_XXX), mapear cada código a un mensaje claro y mostrarlo en la UI. Evitar mostrar raw JSON al usuario. | 30 min |
| 3.5 | Alinear estados (workflows) | En formularios de cambio de estado (sprint, story, release, incident, improvement, change request, document version): dropdowns o botones con solo los valores que la API acepta; enviar exactamente ese valor. Revisar que no se envíen estados obsoletos o inventados. | 45 min |
| 3.6 | Probar flujos end-to-end | Después de cada grupo de cambios: probar login, dashboard, proyectos, features, stories, sprints (cerrar, asignar stories), releases (cambiar estado, asignar feature), incidentes (editar, estado), change requests, improvements, documentos (versiones). Verificar que no hay 404/400 por desalineación. | 45 min |

**Criterio de cierre paso 3:** Código del frontend alineado con la API; errores manejados; workflows correctos.
