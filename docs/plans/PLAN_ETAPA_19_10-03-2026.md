# Plan ETAPA 19 — Dashboard con datos reales — 10-03-2026

**Fecha de ejecución:** 10-03-2026 (Semana 2 — Día 2)  
**Referencia:** docs/CHECKLIST_ETAPAS_PROYECTO.md (Etapas 18–22), docs/ENDPOINTS_API_Y_USO_FRONTEND.md, docs/PLAN_ETAPA_13_REDISENO_DASHBOARD.md  
**Objetivo:** Sustituir datos dummy del dashboard por datos reales de la API; métricas y tarjetas alimentadas por endpoints existentes.

---

## 1. Contexto y meta del día

- **Por qué este día:** Tras validar con pruebas humanas (Día 1), el siguiente paso es que el dashboard muestre solo datos reales: proyectos activos, sprints activos, incidentes abiertos, releases activas, métricas de usuarios cuando aplique. Cero datos hardcodeados o placeholders en las tarjetas y secciones principales.
- **Entregable del día:** Dashboard (#/dashboard) alimentado 100% por la API; eliminación total de datos dummy; validación QA y cierre por PO MASTER.

---

## 2. Actividades detalladas por paso

### Paso 1 — PO MASTER define métricas del dashboard

| # | Actividad | Detalle | Tiempo est. |
|---|-----------|---------|-------------|
| 1.1 | Revisar diseño actual del dashboard | Revisar public/js/views/dashboard.js y public/index.html (si aplica). Listar cada bloque que muestra datos: tarjetas de métricas (Active Projects, Open Stories, Sprint Progress, Critical Incidents), My Assignments, Active Sprint Status, Project Health Overview, Recent Activity Feed, Recent Projects. | 15 min |
| 1.2 | Mapear cada bloque a endpoints | Definir de qué endpoint(s) sale cada dato: proyectos activos → GET /projects (filtrar status ACTIVE y contar); sprints activos → GET /projects/:id/sprints por proyecto o listado que permita contar activos; incidentes abiertos → GET /projects/:id/incidents (filtrar por estado abierto) o agregar; releases activas → GET /releases (filtrar por estado); usuarios → GET /users o /auth/me según contexto. Documentar en una tabla: Bloque | Endpoint(s) | Filtros/transformación. | 25 min |
| 1.3 | Definir “empty state” por métrica | Si no hay proyectos: mostrar 0 en Active Projects y mensaje coherente. Igual para sprints, incidentes, releases. Definir textos y comportamiento (ej. “No active projects” con enlace a crear proyecto). | 15 min |
| 1.4 | Documentar especificación | Redactar breve doc “Especificación métricas dashboard ETAPA 19” (puede ser una sección en este plan o en docs/plans/) con: lista de bloques, endpoint por bloque, criterios de éxito. Entregar a SYSTEM ARCHITECT y MASTER DEVELOPER. | 10 min |

**Criterio de cierre paso 1:** Especificación clara de qué debe mostrar cada parte del dashboard y de dónde sale cada dato (API).

### Paso 2 — SYSTEM ARCHITECT valida endpoints

| # | Actividad | Detalle | Tiempo est. |
|---|-----------|---------|-------------|
| 2.1 | Verificar existencia de endpoints | Comprobar que los endpoints elegidos por PO MASTER existen en la API y devuelven la estructura esperada (GET /projects, GET /releases, GET /projects/:id/sprints, GET /projects/:id/incidents, etc.). Revisar docs/ENDPOINTS_API_Y_USO_FRONTEND.md y si hace falta openapi.yaml o CONTRATO_API.md. | 15 min |
| 2.2 | Validar eficiencia y permisos | Si algún dato requiere muchas llamadas (ej. sprints por cada proyecto), valorar si hay un endpoint de resumen o si el frontend puede hacer N llamadas aceptables. Verificar que los endpoints sean accesibles con el rol del usuario que ve el dashboard (MASTER/EMPLOYEE). | 15 min |
| 2.3 | Aprobar o proponer alternativas | Firmar validación o proponer cambios (ej. “usar GET /reports/projects/:id/summary para X”). Anotar en la especificación. | 10 min |

**Criterio de cierre paso 2:** Endpoints validados; MASTER DEVELOPER puede implementar sin dudas de contrato.

---

### Paso 3 — MASTER DEVELOPER conecta API real

| # | Actividad | Detalle | Tiempo est. |
|---|-----------|---------|-------------|
| 3.1 | Identificar datos dummy actuales | En dashboard.js (y archivos relacionados), buscar literales numéricos, arrays hardcodeados, mensajes tipo “36”, “10”, “75%”, “1” o datos de ejemplo. Listar cada ubicación y qué debe reemplazarlos (llamada a API). | 20 min |
| 3.2 | Implementar llamadas para tarjetas de métricas | Para Active Projects: GET /api/v1/projects, filtrar por status ACTIVE (o equivalente), usar .length o total del response. Para Open Stories: obtener vía GET /projects/:id/features y luego GET /features/:id/stories, o sumar desde listados existentes; si no hay endpoint directo, documentar y usar el más cercano. Para Sprint Progress: GET /projects/:id/sprints, identificar sprint activo, calcular progreso si la API lo da o mostrar “N sprints active”. Para Critical Incidents: GET /projects/:id/incidents (por proyecto) o agregar; contar los que tengan prioridad/estado crítico. Implementar con fetch/axios según patrón del proyecto (api.js). | 45 min |
| 3.3 | Implementar datos reales en secciones restantes | My Assignments: si hay endpoint de asignaciones o actividades del usuario, usarlo; si no, dejar empty state o “No assignments” con datos reales vacíos. Active Sprint Status: datos de GET /sprints o por proyecto. Project Health Overview: lista de proyectos desde GET /projects con status y opcionalmente progreso si existe. Recent Activity Feed: si existe endpoint de actividad reciente, usarlo; si no, mostrar “No recent activity” o lista vacía sin datos fake. Recent Projects: GET /projects, tomar los N más recientes (ej. 5), mostrar con badges reales (ACTIVE/ARCHIVED). | 45 min |
| 3.4 | Eliminar todo dato dummy | Borrar o comentar cualquier literal/array de ejemplo. Asegurar que en ningún caso se muestre un número o texto que no venga de la API (salvo etiquetas fijas como “Active Projects”, “Open Stories”). | 15 min |
| 3.5 | Manejar loading y errores | Mientras cargan las peticiones: mostrar estado de carga (spinner o skeleton). Si una petición falla: no romper el dashboard; mostrar 0 o “—”“Error” en esa tarjeta y opcionalmente mensaje en consola o pequeño toast. | 20 min |
| 3.6 | Probar en local | Con backend levantado y BD con datos reales (aunque sean pocos), recorrer el dashboard y comprobar que todas las tarjetas y secciones reflejan la API. Probar con 0 proyectos, 0 sprints, etc., para ver empty states. | 20 min |

**Criterio de cierre paso 3:** Código del dashboard sin dummy; todas las métricas y listas provienen de la API; loading y errores manejados.
