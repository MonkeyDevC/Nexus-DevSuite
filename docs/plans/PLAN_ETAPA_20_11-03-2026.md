# Plan ETAPA 20 — Conexión de todos los endpoints con el frontend — 11-03-2026

**Fecha de ejecución:** 11-03-2026 (Semana 2 — Día 3)  
**Referencia:** docs/CHECKLIST_ETAPAS_PROYECTO.md (Etapas 18–22), docs/ENDPOINTS_API_Y_USO_FRONTEND.md  
**Objetivo:** Conectar **todos** los endpoints de la API con el frontend. Al cierre del día, el listado en ENDPOINTS_API_Y_USO_FRONTEND.md debe tener 100% de endpoints con uso en frontend (pantalla o flujo que los invoque).

---

## 1. Contexto y meta del día

- **Por qué este día:** Es el núcleo de la meta de la Semana 2: que ningún endpoint quede sin uso en la UI. Incluye: Change Requests, Improvements, Document Versions, Releases (status, features, hotfix), Stories (status, assign), Incidents (PATCH status, edición), Sprints (asignar/quitar stories, status), Organizations, Reports (users/activity), System (metrics ya usado), Auth (admin/test si aplica), Health (opcional: comprobación en admin o footer).
- **Entregable del día:** Todas las pantallas/flujos implementados o integrados para los endpoints que hoy no tienen UI; checklist ENDPOINTS_API_Y_USO_FRONTEND actualizado con “usado en frontend” en todos.

---

## 2. Lista de endpoints a conectar (según docs)

Usar docs/ENDPOINTS_API_Y_USO_FRONTEND.md sección “No usados desde el frontend” y sección 1 como lista maestra. Resumen:

| Área | Endpoints a conectar | Acción en frontend |
|------|----------------------|---------------------|
| Health | GET /health | Opcional: Admin o footer “API status” |
| Auth | GET /auth/admin/test | Opcional: solo si hay pantalla admin test |
| Organizations | GET current, GET by id, PATCH | Vista o sección “Organización” (perfil org, editar nombre, etc.) |
| Stories | GET /stories/:id, PATCH status, PATCH assign | Vista detalle story; formularios cambiar estado y asignar |
| Releases | PATCH status, POST features, POST hotfix, PATCH release | En vista detalle release: botones/forms estado, asignar feature, hotfix, editar |
| Change Requests | POST, PATCH submit/approve/reject/implement | Módulo completo: listar, crear, enviar, aprobar, rechazar, marcar implementado |
| Sprints | PATCH /status, POST/DELETE stories, GET sprint stories | En detalle sprint: cambiar estado, asignar/quitar stories, listar stories del sprint |
| Incidents | GET by id, PATCH status, PATCH incident | Vista detalle incidente; editar; cambiar estado |
| Improvements | POST, GET list, GET by id, PATCH status | Módulo: listar, crear, detalle, cambiar estado |
| Documents | GET by code, POST/GET/PATCH versions, PATCH version status | En detalle documento: versiones, crear versión, aprobar/archivar |
| Reports | GET /reports/users/:userId/activity | Vista o pestaña “Actividad por usuario” en Reportes o Admin |

## 3. Actividades detalladas por paso

### Paso 1 — PO MASTER identifica endpoints sin UI

| # | Actividad | Detalle | Tiempo est. |
|---|-----------|---------|-------------|
| 1.1 | Recorrer ENDPOINTS_API_Y_USO_FRONTEND.md | Abrir el doc y marcar cada endpoint de la sección 1 que en la sección 2 figure como “no usado” o “uso parcial”. Crear lista priorizada: críticos para el producto primero (Change Requests, Improvements, Incidents detalle, Sprints avanzado, Stories assign/status, Releases avanzado, Document versions), luego Organizations, Reports/users/activity, Health. | 25 min |
| 1.2 | Definir vista o flujo por grupo | Para cada grupo: nombre de la vista (ej. #/change-requests, #/improvements, #/incidents/:id), acciones (listar, crear, ver detalle, botones de estado). Documentar en tabla: Endpoint | Vista/Flujo | Acción en UI. | 25 min |
| 1.3 | Entregar lista a SYSTEM ARCHITECT y MASTER DEVELOPER | Lista completa en docs/plans/ o en una hoja “Endpoints a conectar ETAPA 20 — 11-03-2026” para que implementación sea ordenada. | 5 min |

**Criterio de cierre paso 1:** Lista única y priorizada de endpoints sin UI con asignación a vista/flujo.

### Paso 2 — SYSTEM ARCHITECT valida diseño de vistas y prioridad

| # | Actividad | Detalle | Tiempo est. |
|---|-----------|---------|-------------|
| 2.1 | Validar rutas y permisos | Por cada endpoint: verificar método, ruta, permisos (MASTER/EMPLOYEE). Asegurar que el diseño de vistas (qué ve cada rol) sea coherente con la API. | 20 min |
| 2.2 | Validar prioridad y dependencias | Confirmar orden de implementación (ej. Change Requests e Improvements pueden ser paralelos; Document versions dependen de vista detalle documento). Ajustar si hace falta. | 15 min |

**Criterio de cierre paso 2:** Diseño y prioridad validados.

### Paso 3 — MASTER DEVELOPER implementa pantallas/flujos hasta 100%

| # | Actividad | Detalle | Tiempo est. |
|---|-----------|---------|-------------|
| 3.1 | Organizations | Añadir vista o sección (ej. #/organization o dentro de Admin): GET /organizations/current y GET /organizations/:id para mostrar datos; PATCH para editar (MASTER). Enlaces desde menú o dashboard. | 45 min |
| 3.2 | Change Requests | Nueva vista #/change-requests: GET (si existe listado en API; si no, crear endpoint o usar lista en memoria desde POST). Formulario crear (POST), botones Submit (PATCH submit), Approve/Reject (PATCH approve/reject), Implement (PATCH implement). Solo MASTER para approve/reject/implement. | 1 h |
| 3.3 | Improvements | Nueva vista #/improvements: GET list, formulario crear (POST), vista detalle GET by id, PATCH status (dropdown o botones por estado). Enlace en menú. | 1 h |
| 3.4 | Document Versions | En vista detalle documento (#/documents/:id): sección “Versiones”. GET /documents/:id/versions, formulario crear versión (POST), por cada versión opción de actualizar (PATCH) y cambiar estado (PATCH status: aprobar/archivar). | 45 min |
| 3.5 | Releases avanzado | En vista detalle release: botón/forma para PATCH status; formulario o modal para POST features (asignar feature al release); botón/forma para POST hotfix; formulario para PATCH release (descripción, etc.). | 45 min |
| 3.6 | Stories (status, assign) | En listado o detalle de stories: PATCH /stories/:id/status (selector de estado); PATCH /stories/:id/assign (selector de usuario). Vista detalle story si no existe: GET /stories/:id. | 45 min |
| 3.7 | Incidents (detalle, PATCH) | Vista detalle incidente #/incidents/:id o desde proyecto: GET /incidents/:id; formulario edición (PATCH /incidents/:id); PATCH /incidents/:id/status (selector estado). Enlace desde listado de incidentes. | 45 min |
| 3.8 | Sprints (status, stories) | En vista detalle sprint: PATCH /sprints/:id/status (estados según API); lista de stories del sprint GET /sprints/:id/stories; añadir story POST /sprints/:id/stories/:storyId; quitar story DELETE /sprints/:id/stories/:storyId. Corregir si la UI usaba /close → usar PATCH /sprints/:id/status con cuerpo correcto. | 1 h |
| 3.9 | Reports — actividad usuario | En Reportes o Admin: selector de usuario y llamada GET /reports/users/:userId/activity; mostrar tabla o cards con actividad. | 30 min |
| 3.10 | Health / Auth admin test | GET /health: en Admin o en footer mostrar “API: OK” si aplica. GET /auth/admin/test solo si hay pantalla explícita de test; si no, puede quedar como “usado por tests” y no obligatorio en UI. | 15 min |
| 3.11 | Actualizar ENDPOINTS_API_Y_USO_FRONTEND.md | En la sección “Usados en frontend” (o equivalente), asegurar que cada endpoint de la lista maestra figure como usado, con la vista/flujo correspondiente. Revisar que no quede ninguno en “No usados”. | 30 min |

**Criterio de cierre paso 3:** Todas las pantallas/flujos implementados; documento ENDPOINTS_API_Y_USO_FRONTEND.md actualizado al 100% de uso.
